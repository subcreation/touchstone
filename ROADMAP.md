# Touchstone Roadmap

Status: accepted v1 behavior; v0.1 public release in preparation

## Promise

Touchstone keeps a plausible completion claim distinct from a result reality
actually supports. It asks for the strongest relevant observation without
turning proof into performance or ceremony.

## How To Read This Roadmap

- `[x]` means the capability and its witness are accepted.
- `[~]` means a working candidate exists, but an integrated witness, review,
  release gate, or unresolved Mystery remains.
- `[ ]` means implementation remains.

The bold title is the Story. Packaging work appears only inside the Story it
enables. This roadmap adds no routing authority, workflow state, or permission.

## Roadmap

- [x] **An agent and its reviewer accept a works claim only at the evidence
  class actually reached.**

  **Detail:** The accepted v1 behavior runs the real thing first, keeps
  inspection, build, seam, runtime, and physical evidence from substituting,
  states literally what ran and was observed, distinguishes executor
  observation from evidence review and independent rerun, and leaves residual
  human checks visible. It owns none of code simplicity, Git handoff, Mystery
  investigation, or Story wording.

  **Witness:** The frozen `SKILL.md` has governed Current claim-and-acceptance work and survived direct human review without reopening v1. No measured advantage is claimed.

- [~] **People can install the same Touchstone behavior independently of
  Current.**

  **Detail:** This standalone package reproduces the frozen `SKILL.md` (with
  internal team-member names in its examples replaced by roles) and supplies
  one onramp for Codex, Claude Code, and Grok Build, licensing, documentation,
  final hero artwork, and clean lifecycle exercises. Independent review and the
  tagged public release remain.

  **Witness:** A fresh reviewer installs every supported host, verifies the
  exact skill bytes, applies it to one false-green fixture, removes it without
  residue, and confirms a public tag matches the accepted artifact.

- [ ] **People can judge Touchstone against a reproducible false-green
  baseline.**

  **Detail:** Publish deterministic fixtures where inspection, a build, or a
  seam check is green while runtime or physical experience contradicts, then run
  no skill, generic verification guidance, and exact Touchstone.

  **Witness:** Public fixtures, scoring code, and raw isolated runs report
  unsupported completion claims prevented beside final correctness,
  evidence-class accuracy, unnecessary human requests, and turns, tokens, cost,
  and time.

- [ ] **Proof economy is visible: teams see which proof executions change a
  decision.**

  **Detail:** Measure which proof runs change a claim or next action versus
  repeat an established result, without demanding maximum ceremony from small
  claims.

  **Witness:** A public corpus separates decision-changing proofs from
  redundant ones and shows the rule adds no irrelevant ceremony to smaller
  claims.

- [ ] **Current imports an exact Touchstone release without silently drifting.**

  **Detail:** Current consumes one tagged skill through a reviewed manifest and
  deterministic sync path, not a floating branch.

  **Witness:** A controlled update reproduces the tagged skill byte-for-byte,
  shows the intended diff before review, and fails closed on unexpected drift.

- [ ] **Evidence specializations extend to non-engineering work without
  pretending every outcome has a software test.**

  **Detail:** Post-release work tests domain witnesses such as source
  authority, citation, rendered report, human review, delivery, and receipt
  while preserving the claim/evidence boundary. This is not the rejected v2
  communication-compression experiment.

  **Witness:** Matched cross-domain tasks retain evidence-class accuracy while
  loading only role-relevant proof guidance.

## Domain Scope And Specialization

The present skill's evidence classes and examples are weighted toward software
work. Its candidate shared core is matching each claim to the strongest relevant
observation while preventing one evidence class from impersonating another.

Post-release work should test specializations for software gates; research
source authority, citations, supplied packets, rendered reports, and human
review; and
communication delivery, receipt, and response. Each specialization must supply
valid witnesses and residual human checks without weakening the shared boundary
or loading irrelevant proof catalogs into every worker.

## How Progress Is Judged

Primary measure: **unsupported completion claims prevented**.

The benchmark uses false-green tasks where inspection, a build, or a seam check
appears green while runtime or physical evidence contradicts. Score final
correctness, evidence-class accuracy, false completion, unnecessary human
requests, turns, tokens, cost, and time. More proof without a better decision
does not demonstrate value. No comparative efficacy percentage is claimed until
fixtures, raw runs, scoring code, and reproduction steps are public; see
[benchmarks/README.md](./benchmarks/README.md).

## Non-Goals

- General communication compression or terseness.
- A parser, status machine, permission layer, or workflow engine.
- Requiring the largest possible proof for every claim.
- Treating a sentinel, mock, or static inspection as physical observation.
- Declaring success because documentation volume increased.
- Reviving the rejected v2 experiment as present behavior.

## Contributing

Useful contributions provide a concrete false-green example, a smallest
discriminating witness, and a reproducible fixture. Any new rule must name the
claim it protects and show that it does not demand irrelevant ceremony from
smaller claims. See [CONTRIBUTING.md](./CONTRIBUTING.md).

## Direction Status

Current retained Touchstone v1 after matched comparison work did not establish
a v2 efficacy gain. The v0.1 public release preserves that v1 direction and
does not revive the rejected v2 behavior.
